> 지침을 먼저 읽고 구현·측정 근거는 뒤에서 확인합니다.


## 앞으로 지킬 배포·검증 규칙

가격 계산의 영구 캐시는 `cloudflare/dist/housing-cache.sqlite`다. CI는 이 비공개 DB 한 개를 복원·저장한다. 매매·전세·월세 지역 가격과 임대 시장 통계는 `calculation_cache`의 서로 다른 scope를 사용한다. 입력·계산 코드 의존성과 결과 해시를 유지한다. 변경된 묶음만 다시 계산한다. 손상된 캐시 항목은 재계산하며 원천 오류는 숨기지 않는다. 공개용 압축 파일은 DB에서 출력한다. 출력 파일이 손상됐어도 DB 결과가 정상이면 다시 계산하지 않고 출력만 복원한다.

배포와 공개 검증 뒤 `node tools/prune-region-price-cache.mjs --apply`로 가격 캐시를 정리한다. 현재 월·분기에 필요한 DB 항목과 공개 분기 파일은 유지한다. 참조하지 않는 가격 항목, 구형 가격 scope와 기준 계산 scope, 월별 중간 파일을 제거한다. 다른 계산 scope와 원천·승인 DB는 대상이 아니다. 불완전한 새 캐시나 알 수 없는 파일을 만나면 삭제 전에 중단한다. `--apply`가 없으면 목록·용량만 확인한다. CI artifact의 `price-cache-cleanup.json`에 삭제 건수와 바이트를 기록한다. 이 정리는 이전 GitHub Actions 캐시 아카이브의 삭제와 별개다.

단지·임대 시장의 BIN 포장과 검색·지역 가격의 gzip JSON 포장은 같은 비공개 캐시 계층을 사용한다.
계산 결과와 전송 형식의 지문은 구분한다. BIN 포장 지문에는 코덱과 생성된 PolyGen 열을
포함한다. JSON 포장은 해당 직렬화·압축 코드의 지문을 사용한다. 같은 논리 내용과 포장 지문이면 압축 결과를 재사용한다. 최종 파일의 바이트가
같으면 다시 쓰지 않는다. 최초 형식 전환은 새 포장이 필요하다.

검색의 `data/search/catalog/`와 `data/search/latest/`는 각각 32개 gzip JSON 버킷이며
manifest의 `format`은 `gzip-json-records-v1`이다. `.bin` 파일명에는 내용 SHA-256을 넣는다.
이 두 경로와 아래 공동주택 전송 BIN에 1년 `immutable` 캐시를 적용한다. 작은 JSON manifest와
고정 이름 BIN은 Cloudflare 기본 재검증을 유지한다. 자료 URL에 이미 SHA-256 `v`가
있으면 `deployment-version.js`가 이를 배포 SHA로 덮지 않는다. 관련 없는 코드 배포로
검증된 자료의 캐시 키를 바꾸지 않기 위한 규칙이다.
[검색 전송 형식 선택](apartment-and-board.md#공통-단지-자동완성과-검색-자료)은 단지 기준 문서에 둔다.
[Cloudflare 정적 자산 헤더 규칙](https://developers.cloudflare.com/workers/static-assets/headers/)을 따른다.
파일 수 20,000개와 파일당 25MiB 검사는 그대로 적용한다.

공동주택 목록의 생성용 `data/housing-v3/index.json`은 Git과 공식 후보에 유지한다.
CI 공개 자산은 `transport.json`과 원본 SHA 이름의 gzip JSON BIN으로 대체한다.
이번 패키지의 정확한 BIN 경로에만 immutable 헤더를 쓴다. manifest와 다른 경로는
재검증한다. 원문 해시·압축 해시·해제 길이를 연결한 [공동주택 전송 계약](apartment-and-board.md#공동주택-정보의-전송-형식)을 따른다.
이 변환을 다른 생산 파일의 공개 해시 검사 생략에 사용하지 않는다.

브라우저의 매매·전월세 공통 Cache Storage는 256파일·압축 바이트 64MiB를 제한으로
사용한다. 저장 순서에 따라 오래된 항목을 정리한다. 같은 실행환경의 진행 중 요청과
창·Worker 사이의 완료 파일을 재사용한다. 개인 API 응답은 이 캐시에 넣지 않는다.

전월세 시장 통계는 파일 변경과 계산 입력 변경을 구분한다. 거래 파일과 기존 번호표 구간이 같으면 해석·집계를 생략한다. 번호표 끝에 매매 면적이 추가돼도 기존 통계는 유지한다. 분기 파일이나 지역 귀속이 바뀌면 해당 월을 읽고 실제 집계 입력을 비교한다. 면적·보증금·월세·계약 구분·환산율·시도·시군구가 같은 월은 집계를 재사용한다. 행 순서와 중복 건수도 비교한다. 취소 거래는 기존 규칙으로 제외한다. 현재 물리 파일 해시와 실행 종료 시 입력 확인은 유지한다. 자세한 기준과 실측은 [전월세 시장 캐시](rental-market.md#자료와-캐시)를 따른다.

로컬 파일 포장은 지역 거래·상태, 매매 상세, 전월세 상세, 계약 이력의 생산 코드 지문을 따로 저장한다. DB 잠금이나 통계 화면 수정만으로 모든 포장 범위를 무효화하지 않는다. 현재 입력·번호표·결과 바이트와 DB 변경 묶음은 계속 확인한다. 새 범위별 근거가 없는 기존 캐시는 최초 실행에서 다시 구축한다. [파일 생산 의존성](../../15_26/docs/generation-file-batch-candidate.md#파일-생산-코드-의존성과-범위별-지문)이 기준이다.

매매 보완 조회는 상세 포장기의 의존성에서 분리한다. 통합 단지 보완 생성기의 의존성에는 유지한다. 계약 이력은 지역·월 비공개 캐시로 변경 월을 포장한 뒤 기존 지역 파일을 조립한다. 첫 실행에는 새 캐시를 구축한다. [단지 상세 생성 기준](apartment-and-board.md#공통-거래를-사용하는-단지-상세)을 따른다.

로컬 생성기는 `NODO_CACHE_DB`로 `15_26/data/housing-cache.sqlite`를 지정한다. CI는 자체 DB를 사용한다. 전유부 원문·내부 연결·의견·승인 원장을 CI에 업로드하지 않는다. 검증 재사용 기록은 같은 DB의 `cache_artifact`에 저장한다. `cloudflare/dist/validation-cache-v1`은 논리 scope이며 별도 폴더 캐시는 복원·저장하지 않는다. 운영 CI는 주간 완료 기록을 조회·복원·저장하지 않는다.

`tools/cache-store.mjs`는 로컬 지역 입력·번호 풀·계산·포장 캐시와 검증 재사용 기록의 DB 접근을 맡는다. `cache_artifact`는 경로별 참조를, `cache_blob`은 같은 해시의 내용을 한 번 저장한다. 압축된 payload는 조회할 때 기존 바이트로 복원한다. 마지막 참조를 교체·삭제하면 사용하지 않는 payload도 같은 트랜잭션에서 제거한다. 공개 출력은 실제 파일로 쓴다. DB에 없는 항목을 옛 캐시 파일에서 읽지 않는다. Node 종료 시 연결을 닫아 WAL을 반영한 뒤 CI가 DB를 보관한다. 로컬 거래 대표값의 이전·축소·반영·복구와 실제 적용 상태는 [공통 캐시 DB 기준](../../15_26/docs/calculation-cache-candidate.md#공통-캐시-db의-저장-범위)을 따른다.

검증 재사용 기록의 디렉터리와 상위 경로는 `dirname`으로 루트까지 검사한다. Windows 확장 경로의 루트 구분자를 보존하며, 출력·상위 디렉터리·캐시 DB 경로의 링크는 계속 거부한다. 검증 성공 기록의 입력 해시·코드 지문·전체 검사 모드 판정은 바꾸지 않는다.

Node 22는 SQLite 모듈을 불러올 때 실험 기능 경고를 출력한다. 지역 검증기의 import가 CLI를 실행하지 않는지 확인하는 테스트는 해당 자식 프로세스에서만 `ExperimentalWarning`을 억제한다. 종료 코드와 빈 표준 출력·오류 검사는 유지한다. 지역 검증 테스트의 임시 폴더는 캐시 DB 연결을 닫은 뒤 정리한다. 실제 CLI 검증과 운영 빌드의 경고·오류 처리는 바꾸지 않는다.

manifest 해시 확인은 같은 호출에서 동일 경로를 한 번 읽고, 모든 참조의 예상 해시를 각각 대조한다. 호출 종료 전 파일 식별자·크기·수정/변경 시각과 상위 디렉터리 식별자를 다시 확인한다. `verifyHousingRegions` 한 번의 실행 안에서는 `tools/file-hash-memo.mjs`가 경로와 전체 lstat 서명이 같은 파일의 해시를 다시 계산하지 않는다. 읽기 시작 2초 이내에 수정된 파일은 시각 단위 경합 때문에 메모하지 않는다. 서명 비교와 manifest 대조는 생략하지 않으며, 해시 결과는 실행 사이에 보관하지 않는다.

검증 재사용 기록은 성공한 검사의 최적화이며 현재 입력 확인을 대신하지 않는다(`tools/validation-session.mjs`). 기록 schema 2는 지역 번호표를 입력 해시 대신 앞부분 조건(경로·단지 수·면적 수·앞부분 해시)으로 저장한다. 번호를 끝에 추가한 번호표는 기존 기록을 재사용하고, 앞부분이 달라지거나 줄면 일반 검사를 수행한다. 미재사용 원인은 `validationMisses`의 `full`·`missing`·`inputs`·`identity`·`invalid`로 남는다. schema 1 기록과 검사 코드가 다른 기록은 재사용하지 않으므로 변경 후 첫 실행은 전체 검사 비용이 든다. 세부 계약은 [릴리스 계약](../../15_26/docs/site-release-workflow.md)을 따른다. 검사 코드 변경은 기존 의미 검사 증거를 무효화하므로 최초 정식 CI는 현재 코드로 다시 검증한다. 기존 producer 증명을 재서명하지 않는다.

공식 부동산 생성의 비공개 공통 거래 번호 풀은 [번호 풀 파일 검사](../../15_26/docs/housing-packed-storage.md)의 현재 바이트 병렬 검사 경로를 사용한다. 공개 파일/CI 가격 모델·schema를 바꾸지 않으며, 검사 코드가 바뀐 최초 캐시 구축과 정상 재사용 시간을 구분한다. 구간PASS를 새 자료 공개 승인으로 해석하지 않는다.


운영 빌드는 현재 파일 해시와 검사 코드 지문을 확인한 PASS 증거를 재사용한다. 변경·누락·손상은 재검사한다. 매매·전월세 공통 거래는 지역·월, 상세는 각각 지역·연도와 지역·월 단위로 검사한다. 운영 workflow는 push와 수동 실행 모두 `NODO_FULL_VERIFY=0`을 사용한다. 요일이나 주간 완료 기록으로 계산·검사 캐시를 무효화하지 않는다. 현재 입력·출력 해시와 변경 구간 검사, 일반 코드 테스트와 동일 SHA·Worker·공개 manifest·공개 바이트 검증은 유지한다. 단계별 실제 시간은 CI artifact의 `build-timings.json`을 확인한다. 공식 생성기가 검토 산출물에 기록한 비공개 `data/.housing-validation.json`도 재사용한다. 검사 코드와 현재 manifest·참조 파일·상세 조각의 모든 바이트 해시가 일치해야 한다. 기록이 없거나 유효하지 않으면 전체 의미 검사 또는 기존 PASS 캐시 검사를 수행한다. 이 기록은 공개 자산에 포함하지 않는다.


- `main` push → Cloudflare Production: 운영 환경 검사 → 타입·기능·자산 검사 → Worker/정적 자산 배포 → 같은 SHA·manifest·공개 파일 해시·없는 JSON 404 확인 → Google 로그인 시작 확인.
- 연도별 지도 상태가 있으면 공개 검사에서 파일 앞 12바이트를 Range로 요청한다. 206 상태, 정확한 범위·길이와 묶음 식별자를 확인한다. 전체 200 응답은 구간 전송 성공으로 처리하지 않는다. 자산 바인딩의 길이 헤더가 없어도 묶음 헤더로 처리하는 기준은 [지도 상태 저장 계약](../../15_26/docs/housing-packed-storage.md#지도-상태의-연도-묶음)을 따른다.
- 배포 담당자는 동일 SHA의 성공 job과 원본 `verified-release.json`을 확인한다. CI가 끝낸 공개 검사를 수동으로 반복하지 않는다. 생성 자료의 최종 증명 연결은 공식 실행기가 수행한다. 수동 절차는 [공통 배포 기준](../../ops-dashboard/docs/deployment.md)을 따른다.
- `cloudflare-staging` push → Cloudflare Staging: 시험 DB와 Worker만 사용한다. 운영 활성화 여부는 시험 대상 검사의 조건이 아니다.
- 운영 배포는 일반 DB migration, 데이터 초기화, secret 생성/교체를 하지 않는다. 현재 Production YAML에 명시된 승인된 board/member-library 테이블·키 검사는 고정된 대상과 검사 코드를 따르며, 기존 상태를 보존한다. 이 문서는 추가 스키마 승인이 아니다. 현재 D1과 기존 회원/관리자/세션을 보존한다. 스키마 변경은 별도 절차가 필요하다.
- 운영 `AUTH_ENABLED=true`, `MAINTENANCE=false`, `WITHDRAWAL_ENABLED=true`를 소스에 저장했다. 배포마다 임시 옵션으로 켜는 방식은 종료한다.
- Cloudflare Custom Domain과 www 리디렉션은 대시보드에서 관리한다. Wrangler `routes`/`route`는 지정하지 않는다. 설치된 Wrangler는 custom domain 목록이 비어 있으면 도메인 게시를 실행하지 않는다. 배포 후 실제 운영 도메인 접근으로 연결 보존을 검증한다. CI 토큰에 DNS·결제 권한을 추가하지 않는다.
- `tools/deployment-provider.json`과 저장소 변수 `NODESTREAM_DEPLOYMENT_PROVIDER`는 `cloudflare`다. 기존 Pages 완료 후 캐시 Purge 작업은 건너뛴다. GitHub Pages와 Supabase 자체는 아직 삭제하지 않는다.
- 무료 플랜 유지. 운영 환경은 `main`, 시험 환경은 `cloudflare-staging`만 허용한다. 수동 검토자·승인 대기 시간을 추가하지 않는다.
- 빈 DB·비공개 Worker를 전제로 했던 일회성 `cloudflare-prepare-production.yml`은 제거했다. Git 이력에서 확인 가능하며 공개 이후 재실행하지 않는다.
- 수집 일정과 공개 데이터는 이번 연결 작업에서 재생성하지 않는다. 생성기는 공통 provider 계약을 읽어 Cloudflare 공개 검증 경로를 사용해야 한다.
- 6시간 주기 Health는 별도 활성 변수로 켠다. 자동 비용 측정은 구현되어 있지 않으며 무료 플랜에 유료 가입이나 비용 차단을 추가하지 않는다.

운영 환경 변수: `CLOUDFLARE_PRODUCTION_ENABLED=true`, `CLOUDFLARE_PRODUCTION_AUTH_APPROVED=true`, `CLOUDFLARE_PRODUCTION_WRITES_APPROVED=true`, 기존 계정/D1 ID와 `CLOUDFLARE_WORKERS_PLAN=free`.

전월세는 사용자 결정(2026-10-03)에 따라 기존 원천별 대표가격·가중치·건수·지역 귀속을 유지한다. 승인된 공개 단지별 내부 캐시에는 소속 원천의 기여 자료를 함께 저장하되 집계할 때 원래 원천 순서를 복원한다. 공개 단지로 가격을 하나로 합치거나 지역 간 원천의 기존 집계 귀속을 변경하지 않는다. 매매는 기존 공개 단지 그룹 계산을 유지한다. 승인 연결 변경은 관련 묶음을 무효화하며 원천 번호·승인 자체는 변경하지 않는다.

지도 가격의 내부 캐시는 위의 비공개 SQLite DB를 사용한다. `cloudflare/dist/region-price-cache-v2`는 공개 파일을 포장하기 위한 출력 위치다. 월별 작은 기록에 입력·엔진·결과 해시와 크기를 저장한다. 사용한 번호·정확 면적·공개 연결 목록은 별도 압축 항목에 저장한다. 현재 입력과 연결 정보가 같으면 이 목록과 그룹별 결과를 읽거나 해석하지 않는다. 연결 정보가 바뀌면 해당 월이 사용한 번호만 대조한다. 매매의 다른 시도 연결 변경은 이전·현재 원천과 공개 그룹의 귀속을 확인해 제외한다. 시도 간 이동은 양쪽 결과를 갱신한다.

연간 상태나 거래 분기가 바뀌면 해당 월의 실제 상태 지문을 비교한다. 상태가 같은 월은 그룹 결과 조회·결과 조립·압축을 생략한다. 상태 지문은 행 순서·중복·가격·날짜를 보존한다. 전세·월세의 상대 유형에만 새 날짜가 생겨도 기존 빈 날짜 프레임을 유지한다. 가격 입력이 바뀐 월만 그룹별 가격 증거를 대조하고 다시 조립한다.

분기는 월별 기록의 결과 해시와 현재 분기 payload를 먼저 확인한다. 재사용할 수 있으면 월별 결과 payload를 읽지 않는다. 다시 묶어야 하는 분기만 소속 월 결과를 읽는다. schema 3 입력에서는 중간 월 BIN을 파일로 출력하지 않고 비공개 DB에 유지한다. 사용하지 않는 월·그룹 캐시를 매번 전수 검사하지 않는다. 필요한 캐시가 손상되면 그 항목을 재구축한다. 공개 분기 파일의 현재 바이트 확인·복원과 현재 입력 해시·종료 전 입력 불변 검사는 유지한다. 공개 경로·schema는 바꾸지 않는다. 최신 임대 계약일도 현재 입력에 결합된 작은 기록을 재사용한다.

전세·월세는 동일 지역·월의 조립한 상태를 한 달까지만 공유한다. 낮은 단계의 해석한 분기·연간 상태는 CI에서 유형별 추정 보관 비용 1GiB·최대 1,024항목의 LRU 캐시를 사용한다. 연간 상태는 압축 열과 월별 참조 배열의 실제 보관 형태로 비용을 추정한다. 다른 판독기의 기본 네 항목 정책은 유지한다. 현재 물리 파일 해시는 실행 내 공유하고 종료 전에 다시 확인한다. `rentalStateParses`는 지역·월 조립 횟수이며 실제 물리 파일 해석·재사용은 `regionPriceStats.housingDecodeCache.sale/rental`의 hits/misses/evictions와 추정 보관 비용으로 확인한다. RSS는 별도 실측한다. [구간별 생성 캐시 계약](../../15_26/docs/generation-file-batch-candidate.md#구간별-생성-캐시-계약)를 따른다.

`build-timings.json`의 `regionPriceStats`에서 계산/재사용 그룹 수와 가격 재계산 없이 표시 정보만 갱신한 decoratedGroups, 월·분기 재사용과 무효화 원인(missing/inputs/engine/corrupt)을 확인한다. 그룹 수는 고유 단지 수가 아니라 그룹·월·뷰의 계산 또는 재사용 단위 수다. 월별 기록으로 재사용한 그룹 수는 그룹 payload를 실제 조회한 횟수가 아니다.

`semanticReusedMonths`는 물리 입력이 바뀌어도 실제 상태가 같아 조립을 생략한 월 수다. `assembledMonths`는 결과를 조립한 월 수다. `bindingsDecoded`, `groupPayloadReads`, `monthPayloadReads`, `quarterPayloadReads`, `receiptReads`, `latestRowsReads`로 조회·해석 횟수를 구분한다. `saleStateParses`는 전국 매매 상태를 조립한 월 수이며 `rentalStateParses`는 전월세 지역·월 수다. `phaseTimings`는 초 단위로 입력 확인, 상태 해석·지문, 캐시 읽기·쓰기, 연결 대조, 그룹 해석·계산과 조립, 월 압축, 분기 조립, 파일 출력, 종료 전 입력 확인을 나눈다. `total`은 전체 벽시계 시간이다. 실행하지 않은 단계 키는 생략한다.

처음 새 엔진과 월별 기록을 구축한 비용은 이후 변경 처리 시간과 구분한다. 이전 증명을 새 코드로 재서명하지 않는다. 그룹·월 증거는 공개 자산이나 Git에 넣지 않는다. 비공개 DB 크기와 CI 복원·저장 시간은 해당 실행에서 따로 측정한다. 원천 오류를 캐시 손상처럼 처리하거나 전체 검사 모드를 우회하지 않는다. 구간 비교와 결과 대조는 15_26 Git 이력의 `docs/generation-storage-cache.md`에 남아 있다.

### 운영 배포와 별도 전체 검산

운영 배포는 주간 완료 기록의 존재나 날짜를 실행 조건으로 사용하지 않는다. 기존 기록을 삭제하거나 성공으로 바꾸지도 않는다. 검증된 계산 캐시가 있어도 일요일·수동 실행이라는 이유만으로 전체를 다시 계산하던 연결은 제거했다.

전체 검산이 필요하면 아래 복사본 성능 시험처럼 별도 작업으로 실행한다. `NODO_FULL_VERIFY=1`은 그 검산 프로세스에만 지정한다. 검산 도구와 기존 시험은 보존한다. 검산 결과나 과거 주간 완료 기록을 정상 배포의 선행 조건으로 연결하지 않는다.

`build-timings.json`은 실제 실행의 `fullVerification`과 `verificationEngine`을 기록한다. `verificationEngine`은 이번 빌드 중 검사·계산 코드 변경을 확인하는 지문이다. 주간 완료 여부를 조회하지 않는다. 계산 캐시는 공개/Git에 포함하지 않는다. 새 계산 로더·검사 의존성을 추가하면 현재 코드 지문에 포함되는지 확인한다.

### 복사본 성능 시험

`node tools/benchmark-region-prices.mjs --root FIXTURE --report NEW_JSON`으로 전체 가격 파일의 이번 시간·해시·재사용 수를 남긴다. `--reference`는 기존 모델 계산, `--compare REFERENCE_JSON`은 모든 공개 분기 압축 해시 비교다. 기존 보고서를 덮어쓰지 않는다.

`node tools/benchmark-region-price-changes.mjs --root FIXTURE --report NEW_JSON`은 `fixture.json`에 `isolated:true`인 공개 입력 복사본에서만 번호 추가·신규 거래·가격 정정과 기존 모델의 변경 분기 비교를 수행한다. 운영 사이트·DB 루트는 거부한다. 시험 데이터는 finally에서 복원하지만 프로세스가 강제 종료되면 해당 시험 복사본을 보존하고 조사한다. 시험 캐시·합성 거래를 운영으로 복사하거나 공개하지 않는다. 큰 JSON 보고서·로그는 전체를 터미널에 출력하지 않고 필요한 상태·시간·오류 필드만 읽는다. 한 줄 JSON 로그에 Get-Content -Tail을 사용하면 완료된 작업의 로그 표시만 오래 남을 수 있으므로 실제 result의 완료 상태와 프로세스를 따로 확인한다. `--months`를 사용한 수치는 해당 구간의 시험이며 전체 CI 시간으로 해석하지 않는다. 입력 복사와 최초 캐시 구축 비용은 변경 입력 계산 시간과 분리한다.

패키지는 자산 18,261개와 배포 메타데이터 3개로 총 18,264개였다. 최종 검색 manifest의 64개 gzip JSON과 시장 BIN 16개의 경로·해시·형식을 확인했다. 검색의 실제 읽기 코드도 최종 manifest로 각각 20,917개 레코드를 읽었다. [최종 포장 검산](../../_ops/reports/packed-transport-20261023/package-audit.json)과 [단계별 실행 기록](../../_ops/reports/packed-transport-20261023/build-timings.json)을 보관한다.

이 실행은 앞선 실행에서 만든 계산 캐시를 사용했다. 최초 실행은 마지막 검색 코드 수정이 감지되어 포장 단계에서 중단됐다. 최종 실행의 파일 쓰기 95개와 재사용 18,169개를 깨끗한 기준 배포와의 변경량으로 해석하지 않는다. 운영 단지 JSON의 공식 BIN 교체와 원격 배포는 실행하지 않았다. 패키지의 Git SHA는 로컬 HEAD이며 미커밋 변경이 포함된 이 결과를 동일 SHA의 운영 증명으로 사용할 수 없다.

공개 단지 통합 변경은 운영 CI에서 `test-apartment-groups.mjs`와 `test-group-sale-completion.mjs`를 실행한다. 대표 ID·구성원 필터·공유 거래의 정확 면적·중복·취소 상태와 가격 요약을 확인한다.

## Worker와 API 계약

`cloudflare/`의 Worker는 정적 자산을 먼저 처리하고 `/api/*`와 `/auth/*`만 Worker가 처리한다. SPA fallback은 없다. `www` 리디렉션은 Worker가 아닌 zone 설정이다. `wrangler.jsonc`의 최상위 설정은 시험(staging) D1을, `--env production`은 별도 운영 D1을 선택한다. D1 ID는 공개 식별자이며 비밀값이 아니다. 시험 환경은 시험 사용자와 함께 유지하며 초기화하지 않는다. 마이그레이션 `0001_initial.sql`은 새 빈 DB 전용이며 기존 DB에 다시 실행하지 않는다. 스키마 2가 코드 배포의 전제다. `0002_withdrawal_requests.sql`은 추가형이다.

로컬 검증은 `npm ci --ignore-scripts`, `npm run typecheck`, `npm run test:api`다. 시험은 실제 Worker를 번들하고 Miniflare 임시 D1과 Google HTTP 모의를 사용한다. `.env`·운영 ID·실계정·원천 DB·외부 Google 요청이 필요 없다. `npm run build` 뒤 `node cloudflare/dev-preview.mjs`는 가짜 자료와 Google 외부 요청 차단 상태로 포트 8795에서 loopback 미리보기를 제공한다. 출력되는 가짜 세션은 로컬 UI 시험 전용이며 점검이 끝나면 종료한다.

**인증 전환 경계.** 운영 기본은 `AUTH_ENABLED=false`, `MAINTENANCE=true`다. Google 자격 증명은 Worker secret으로만 설정하고 vars·Git·로그에 넣지 않는다. `AUTH_ENABLED=true`는 `MAINTENANCE=true`여도 새 회원을 만든다. 유지보수 모드는 프로필·댓글·태그·계정 쓰기를 막고 세션 읽기는 허용한다. 인증을 끄면 새 OAuth 교환만 막으며 기존 세션을 폐기하지 않는다. OAuth는 PKCE S256, HttpOnly 쿠키에 묶인 10분 일회성 state, nonce·issuer·audience·만료와 Google JWKS의 RSA 서명 검증을 쓴다. 첫 로그인은 임의 내부 UUID와 `user` 역할을 만든다. 이메일은 계정 병합 키가 아니다. 관리자 지정은 D1 콘솔에서 사용자 ID와 Google subject를 확인한 뒤 `node cloudflare/admin.mjs --env staging|production --user UUID --google-sub VERIFIED_SUB --confirm-grant-admin`으로만 한다. 두 식별자가 모두 일치해야 하며 첫 사용자 관리자 대체 경로와 공개 역할 지정 API는 없다. 탈퇴 재확인은 `/auth/google?reauth=1&withdrawal=1&returnTo=/account/`와 시작 영수증으로 현재 세션·같은 Google `sub`에 묶인다. 이는 선택한 계정의 확인이며 Google이 비밀번호를 다시 물었다는 약속이 아니다. 탈퇴·복구 정책과 API는 [회원 운영 문서](account-withdrawal-google-design.md)가 기준이다.

**브라우저 계약.**

- 모든 API 응답은 `Cache-Control: no-store`다. 오류는 `{error:{code,message}}`이며 SQL·자격 증명을 포함하지 않는다.
- 변경 요청은 정확한 `Origin=SITE_ORIGIN`, 유효한 세션, `/api/session`의 `X-CSRF-Token`이 필요하다. JSON 본문은 `Content-Type: application/json`이며 16KiB 제한으로 읽는다. 소유권·관리자 역할은 서버가 세션에서 정한다.
- `GET /api/session`은 `{session,profile,isAdmin,csrfToken}`을 반환한다. `GET/PATCH /api/profile`의 닉네임은 2~20자 한글·영문·숫자·`_`·`-`이며 대소문자 무시 고유다. `POST /api/logout`, `DELETE /api/account`는 탈퇴 확인 별칭이며 즉시 삭제가 아니다.
- 댓글: `GET /api/comments?page_id&offset&limit`는 루트 댓글 수를 count로 반환하고 루트마다 미리보기를 최대 3개, 전체 응답 100행 이내로 포함한다. `GET /api/comments/:id/replies`는 최대 100개다. 작성은 16~100자 `Idempotency-Key`가 필수이며 같은 키에 다른 내용은 거부한다. 본문 1,000자, 답글은 한 단계다. `PUT /api/comments/:id/like`는 원하는 상태를 설정한다. 관리자가 숨긴 루트는 답글과 함께 접근할 수 없다. 삭제·탈퇴한 루트는 다른 활성 회원의 답글이 있으면 자리표시로 남는다.
- 태그: `GET /api/stocks/:ticker/tags`, `POST`(2~30자 이름, 6자리 종목, 작성자 추천을 한 D1 batch로 처리), `PUT /api/tags/:id/vote`.
- 관리자: `GET /api/admin/stats`, `GET /api/admin/comments`, `PUT /api/admin/comments/:id/moderation`. 삭제한 댓글은 복구할 수 없다.
- `GET /api/health`는 `{status,gitSha,workerVersionId,schemaVersion:2,maintenance}`를 실제 테이블·열 확인 뒤 반환한다. 지원하지 않는 스키마는 503, 누락 테이블은 500이다. 원격 배포 검증은 `workerVersionId`가 비어 있지 않아야 한다.
- 속도 제한은 원자적 고정 창이다. 인증된 쓰기 사용자당 분당 30회, 태그 제안 UTC 일 20회, OAuth 시작 IP 해시당 분당 20회다. 만료 세션·OAuth state·카운터는 매시간 테이블당 최대 1,000행씩 정리한다.
- 탈퇴 기능에는 시험·운영별 64자리 hex `WITHDRAWAL_ENCRYPTION_KEY` secret과 `WITHDRAWAL_ENABLED=true`가 필요하다. 기능을 꺼도 만료 정리를 멈추거나 탈퇴 회원의 로그인을 허용하지 않는다.

**롤백 경계.** 인증·공개 쓰기를 켠 뒤에는 새 D1 자료가 원본이다. 코드 롤백은 같은 D1 바인딩과 호환 스키마를 유지해야 하며 역마이그레이션이나 D1 자동 되감기는 없다. 호환성이 불확실하면 정적 자산을 유지한 채 유지보수 모드로 전환한다. 탈퇴 상태가 생긴 뒤에는 회원 상태를 무시하는 스키마 1 코드로 되돌리지 않는다. 탈퇴·정리 회원을 차단하는 버전만 호환된다.

## 네이티브 투영 CI

`tools/native-projection`의 `npm run test:daily`는 기존 Rust 일별·임대 구현을 빌드해 고정 기준 사례를 실행한 뒤 브라우저 모델·클라이언트 시험을 실행한다. Python을 호출하지 않는다. 시험된 도구는 Rust 1.92.0과 Node 22.18 이상이다. `npm run build:daily`는 stdin의 `daily-build` JSON 요청(`site`, `database`, 선택 `missing`·`cache_dir`)을 받으며 예약 운영 빌드는 운영용 Rust release 실행 파일과 공개 가드를 사용한다. 운영 DB·자격 증명·수집·공개는 이 시험이 쓰지 않으며 Rust 자식 프로세스의 PATH는 비어 있다.

`vendor/`는 `15_26/rust/src`에서 생성한 소스 스냅샷이며 두 번째 구현이 아니다. `provenance.json`이 기준 커밋과 소스·내보낸 파일의 SHA-256을 기록한다. 6개 모듈은 바이트 단위로 복사하고 가드 모듈은 수집기 진입점 앞부분만 포함한다. 배포 CI는 이 고정 스냅샷만 시험하며 인접 운영 저장소를 읽지 않고 최신 소스와의 일치도 증명하지 않는다. 선택 검사 `NODO_NATIVE_SOURCE`는 기록된 해시와 정확히 일치해야 한다. 운영 변경이 이 고정 시험 패키지에 영향이 없으면 소스 동기화를 릴리스와 분리한다.

기준 구현을 바꾼 뒤에는 `node tools/sync-native-projection.mjs <15_26/rust>`, `npm run test:daily`(Rust 빌드는 `--locked`)를 실행한다. 독립 CI 패키지는 고정 lockfile을 유지하며 내보내기는 각 registry 의존성이 운영 lockfile의 정확한 버전·체크섬 부분집합인지 확인한다. 소스 해시와 생성 diff를 검토한다. 운영 저장소의 `node tests/run_projection_native.mjs`는 내보낸 소스·운영 실행 파일이 기준 소스와 일치하는지도 확인하며 CI는 내보낸 파일 해시를 항상 확인한다. 소스 갱신이 기대 출력을 자동으로 바꾸지 않는다.

`fixtures/`는 합성 SQL 입력, 원본 입력 바이트, 기대 데이터 해시와 manifest 필드를 보관하며 운영 DB 자료는 없다. 빈 월·잘못된 날짜·정확 면적·동률·취소·누락 거래·수치 극단·환산율·과거 정정·월 장부 개정을 포함한다. 시험기는 복호화한 모든 데이터 파일을 SHA-256으로 바이트 대조하고 비압축 자산·파일 집합·manifest·소스 체크섬·독립 계산 버전을 확인한다. 압축 바이트는 zlib·플랫폼에 따라 다를 수 있으나 복호화 바이트 기대는 완화하지 않는다. 따뜻한 재사용과 단계 간 재사용은 생성 바이트를 보존해야 하고 원천 DB는 변하지 않아야 한다. 손상 캐시·유지보수 게이트·잘못된 속성 형식·환산율·빌드 중 원천 변경은 실패하거나 복구해야 한다. 기대 출력은 동작 변경을 독립 검토한 뒤에만 재생성하며 실패하는 기대를 현재 Rust 출력으로 자동 교체하지 않는다.
