# 통합 아파트 상세와 공용 게시판

> 문서 역할: **기능·구현 설명** · [문서 목록](README.md)
> 현재 운영·공개 자료 계약은 문서 목록의 기준 문서를 따릅니다. 날짜·건수·성능 수치는 해당 검증 조건의 기록입니다.


## 구현

- 모든 공개 페이지에서 공통 메뉴와 라이트·다크·시스템 테마를 사용한다.
- 검색·비교·실거래·지도·단지정보에서 아파트 선택 시 `/apartment/`로 이동한다. 전월세는 확인된 기존 aptSeq가 있는 단지만 연결한다.
- 상세는 개요, 실거래, 전월세, 투자분석, 단지정보, 위치, 의견 7개 탭이다. 평형과 탭을 URL에 저장한다.
- 최신 유효 거래와 최근 평균가의 기간·건수를 각각 표시한다. 해제·원천에서 사라진 거래는 통계에서 제외하되 내역에서 확인할 수 있다.
- 단지 전체 세대수와 선택 평형 세대수를 구분한다. 여러 원천이 연결된 단지의 미확인 주차·용적률·평형 세대수는 임의 합산하지 않는다.
- 기존 `apt_<row id>` 의견을 그대로 조회한다. 여러 원천 평형이 연결된 경우 의견 원천을 선택한다.
- `/board/`에서 제목·내용 검색, 글 작성·수정·삭제, 댓글을 제공한다. 운영자는 공지 고정과 글 숨김·복구를 할 수 있다.
- 읽기는 공개, 쓰기는 기존 로그인·닉네임·CSRF·속도 제한·탈퇴 처리 정책을 따른다. 글 제목은 기존 댓글 본문의 첫 줄에 저장해 탈퇴 시 기존 삭제 정책을 적용한다.

  거래 참조·계약기간·계약 구분·해제일·종전 금액·갱신권만 담는다.
  거래일·면적·층·현재 보증금·월세를 다시 저장하지 않는다.
- 기존 월별 계약 목록과 표시 사전, 오피스텔·연립 자료는 유지한다.

### 단지 정보와 호환 URL

현재 리뷰 계약에서 `npm run build:apartments`는 생산자가 준비한 DTO의 원천 연결을 확인하고 그대로 재사용한다. JSON을 BIN으로 자동 전환하거나 진입 색인을 다시 쓰지 않는다. `npm run build:apartments -- --verify`는 준비된 자료의 파일 해시와 상세 참조를 검증한다. 원본 DB와 연결 승인 상태는 수정하지 않는다.

운영 자료의 BIN 전환은 [공식 Rust 릴리스](../../15_26/docs/site-release-workflow.md)의 격리 후보 생성 경로가 담당한다. 후보의 최종 BIN과 이전 JSON 폐기 목록을 함께 검토한다. 직접 명령은 기존 JSON index가 있는 구 계약 작업 공간에서도 BIN 전환 쓰기를 거부한다. 기존 자료가 없는 구 계약 fixture의 생성 기능은 유지한다. 파일을 직접 삭제하거나 배포 패키지에서 숨겨 전환을 대신하지 않는다.

변경된 생성·읽기 코드는 상세 256개와 요약 256개를 `packed-records-v1` BIN으로 처리한다. gzip 해제 후의 magic은 `PGRCD001`이다. 단지 ID 색인으로 선택한 단지만 복원한다. 상세 객체 전체를 미리 만들지 않는다. 가격·면적 등 숫자는 f64로 보존한다. 물리 형식은 [공개 저장 규칙](../../15_26/docs/housing-packed-storage.md)을 따른다.

| 파일 | 역할 |
| --- | --- |
| `data/apartments/<묶음>.bin` 256개 | 단지 기본 정보, 평형, 가격 요약, 원천 행과 의견 경로를 담은 상세 DTO |
| `data/apartments/summary/<묶음>.bin` 256개 | 관심 단지와 회원 API에 필요한 이름·지역·평형·최근 거래 요약 |
| `data/apartments/index.json` | 전체 별칭·이전 행 연결과 BIN 해시를 보관하는 생성·검증 기준 |
| `data/apartments/entry-index.json` | entry schema 3의 공통 metadata, 거래 manifest 기준 해시, BIN 해시와 진입 묶음 해시 |
| `data/apartments/entry/<묶음>.json` 64개 | 별칭·이전 행의 단지 ID와 묶음 번호, 실제 원천 지역·번호 연결 |

`js/apartment-entry.mjs`는 작은 `entry-index.json`을 먼저 읽는다. 이어서 선택 ID에 필요한 진입 묶음만 해시로 검증하고 캐시한다. 공통 `updated`, `propertyUpdated`, 원천 해시와 거래 기준 해시는 각 묶음에 반복하지 않는다. BIN 해시도 공통 색인에서 결합한다. 기준일이나 BIN 내용만 바뀌면 진입 묶음 64개를 다시 쓰지 않는다. 별칭이나 이전 행 연결이 바뀌면 해당 진입 묶음만 바뀐다.

`js/apartment-records.mjs`는 필요한 BIN을 내려받아 해시를 검증하고 gzip을 해제한다. 파일과 열린 색인은 제한된 캐시에 보관한다. 선택 DTO는 조회할 때 복원하며 객체 자체를 공용 캐시에 저장하지 않는다. 공통 기준일은 manifest에서 복원한다. 단지별 다른 기준일, 누락 필드와 `null`은 구분해서 보존한다. 기존 JSON DTO와 entry schema 2도 읽을 수 있다.

Rust 생산자는 `propertyUpdated`를 DTO와 단지 index에 같은 null·날짜 값으로 넣는다. 이 공통 필드도 상속 대상이다. 주택 정보 기준일만 바뀌어도 상세 BIN 256개가 모두 바뀌는 일을 막는다.

`tools/build-apartment-records.mjs`는 비공개 포장 캐시를 사용한다. codec 지문과 공통 기준일을 분리한 논리 내용이 같으면 기존 gzip BIN을 재사용한다. 출력 바이트가 같으면 파일을 다시 쓰지 않는다. 원천 해시와 진입 manifest의 연결 검사는 유지한다. 전월세 manifest의 단지 색인 해시와 진입 색인은 최종 BIN 색인에 맞춰 갱신한다.

native 생성의 `cacheDir`는 `tools/cache-store.mjs`가 관리하는 가상 경로다. 포장 캐시는 그 경로의 `apartment-records-v1` 키를 사용한다. 기존 공통 `data/housing-cache.sqlite`를 재사용하며 가상 경로 아래에 별도 DB를 만들지 않는다. `cacheDir`가 없는 단독 실행은 출력 작업 공간의 비공개 캐시를 사용한다.

2026-10-23에는 기존 로컬 공개 자료의 단지 20,915개를 격리 출력으로 변환했다. 상세와 요약 각각 256개 파일의 모든 레코드가 원본과 같았다. 재실행은 BIN 512개를 재사용했고 다시 쓰기 0개였다. 별도 회귀에서는 상세 값 1곳 변경 시 BIN 1개만 포장했고, 나머지 511개의 해시와 수정 시각을 유지했다. [전체 대조 결과](../../_ops/reports/packed-transport-20261023/apartment-audit.json)는 일회성 검산 기록이다. 정상 생성이나 서버 시작의 실행 조건으로 쓰지 않는다.

같은 gzip level 6으로 비교하면 상세 합계는 JSON 33,248,351바이트에서 BIN 31,061,328바이트로 줄었다. 요약 합계는 JSON 4,142,993바이트에서 BIN 5,524,405바이트로 늘었다. BIN이 항상 더 작다는 뜻은 아니다. 선택한 단지만 복원하고 바이트·색인을 재사용하는 것이 주된 목적이다. 4개 상세 묶음의 압축 해제부터 첫 선택 복원까지는 Node 표본에서 JSON 7.95~10.29ms, BIN 6.12~9.10ms였다. 요약 표본의 첫 조회는 대체로 비슷했다. [선택 조회 측정](../../_ops/reports/packed-transport-20261023/selected-read-audit.json)은 네트워크와 화면 표시 시간을 포함하지 않는다.

앞선 2026-10-23 격리 검산에서는 공식 native 자료 생성, 운영 자료의 BIN 전환, 배포를 실행하지 않았다. 운영 반영 상태는 [공식 릴리스 기록](../../15_26/docs/site-release-workflow.md)의 run과 같은 SHA의 CI·공개 검증 근거를 따른다.

같은 격리 출력의 Chrome 표본에서는 대흥동세양의 상세 패널과 전체 화면을 확인했다. 이름·주소·세대수·평형·최신 거래·최근 평균·거래 건수가 원본 DTO와 같았다. entry와 선택 BIN을 읽었고 기존 상세 JSON이나 전체 단지 index로 돌아가지 않았다. 두 번째 문서에서는 BIN 추가 다운로드가 없었다. [브라우저 검증](../../_ops/reports/packed-transport-20261023/apartment-cua-result.json)은 상세 화면만 대상으로 한다. 이 부분 출력 서버에는 홈 검색 manifest를 제공하지 않았다.

현재 리뷰 계약에서 상세의 단지 세대수는 해당 공개 항목의 `units`를 따른다. 여러 원천을 묶은 공개 항목의 세대수가 미확인이면 `null`이다. 이 값을 개별 원천 행의 `tu`로 채우지 않는다. 현재 원천 행은 미확인 평형 세대수 `u`를 생략한다. 상세의 평형과 원천 행은 `units:null`로 표시한다.

`npm run test:site`의 자료 검사는 상세 전체를 순회한다. 단지·평형 세대수 범위, 거래 소유 연결, 대표 행 묶음, canonical ID, 원천 행과 `apt_<row id>` 의견 경로를 대조한다. 한 canonical ID에 여러 대표 행 묶음이 있어도 각 원천 행의 의견 경로는 유지한다. 이 검사는 별도 시험이며 생성기나 브라우저의 정상 실행 조건에 넣지 않는다.

새 경로는 `/apartment/?id=<aptSeq 또는 publicationId>&area=85&tab=overview`이다. 기존 검색 `#a=...&ar=...`, `#i=...`, 지도 상세 및 K-APT `#k=...` 링크는 새 화면으로 이어진다. `row=0`도 유효한 이전 식별자다.

직접 접속 가능한 `/kapt-v2.html`은 `data/housing-v3/index.json`을 읽는다. 구 압축
sidecar를 먼저 읽지 않는다. 현재 계약에서는 공개 목록 수와 `review.approved`가
참인 개별 검토 승인 수를 구분한다. 유형별 건수는 실제 목록에서 계산한다. 면적별
요약이 없으면 미제공으로 표시하며, 메타데이터만 있는 항목을 임대로 단정하지 않는다.
구 승인 JSON도 지원한다. 아파트의 이전 별칭은 통합 상세로 이어진다.

현재 리뷰의 `building-status.json`은 대장 연결 상태를 표시한다. `active`는 현행
대장 연결, `closed`는 폐쇄·말소 대장 이력, `partial_closed`는 현행과 폐쇄 이력의
혼재 또는 일부 폐쇄, `unknown`은 상태 미확인이다. 현재 계약의
`demolitionConfirmed=false`를 유지한다. 폐쇄·말소를 철거로 바꾸지 않으며,
미확인·일부 폐쇄·폐쇄 항목은 이 상태만으로 기본 목록에서 숨기지 않는다.
상태 파일을 받지 못하거나 현재 계약의 항목이 없으면 현행으로 추정하지 않는다.

`node tools/verify-redevelopment-data.mjs`는 상태와 주택 메타데이터의 계약·원천
버전, 지번별 거래 원천 ID를 대조한다. 현재 계약에 구 멸실 플래그나 철거 확정을
섞으면 실패한다. 기존 재건축 관계의 근거·범위·이전/후속 연결 검사도 유지한다.
현재 거래 index 밖의 이전 단지는 `redevelopment-decisions.json`의 같은 지번 키,
명시 상태·이름, 관계와 일치하는 근거 ID가 있을 때만 역사 관계로 확인한다. 이 판정은
현재 단지의 대장 상태를 덮거나 미확인을 재건축·멸실로 바꾸는 데 쓰지 않는다.
별도 `Verify redevelopment data` CI가 이 검사를 실행한다. Production 빌드는
이 명령을 호출하지 않으며, 현재 상태의 화면 회귀시험은 Production 시험에 포함된다.

공식 Rust [부동산 릴리스](../../15_26/docs/site-release-workflow.md)에서 자료 갱신 후 상세 자료를 생성·검증한다. 매매/전월세 계약 상세는 [공통 거래 참조](../../15_26/docs/housing-packed-storage.md)를 사용한다. 단지 DTO·요약 BIN은 공통 거래 원문을 대체하지 않는다. 사이트 빌드는 원천 해시와 상세 자료가 다르면 중단한다. 브라우저도 단지 및 거래 파일 해시를 검증한다.


## 로컬 확인

### 현재 리뷰 자료의 격리 미리보기

현재 리뷰의 [공개 후보 내보내기](../../ops-dashboard/housing-review/docs/hub-source.md#현재-리뷰의-공개-후보-내보내기)로 새 `_ops` 폴더에 후보를 만든다.
`tools/prepare-current-review.mjs`는 그 후보의 행정동과 상세 자료를 준비한다. 요청 JSON은 `baseline`, `candidate`, `pipeline`, `adminSource`, `runtime`, `runtimeSha256` 경로와 값을 받는다.
`baseline`은 기존 공개 저장소다. `pipeline`은 기존 Rust `nodostream-pipeline` 실행 파일이다.

```text
node tools/prepare-current-review.mjs REQUEST_JSON
node tools/prepare-current-review-search.mjs BASELINE CANDIDATE
node tools/preview-current-review.mjs CANDIDATE
```

미리보기는 `http://127.0.0.1:8794/map/`이다. 운영 DB·공개 파일·사용자 의견에는 쓰지 않는다.
후보의 `candidateOnly=true`, `approvedOnly=false`를 유지한다. 공개 패키지는 후보 자료를 거부한다.
기존 단지 ID·별칭·평형 행·댓글 ID·가격 통계는 재사용한다. 필지 차이만으로 기존 단지를 나누지 않는다.
같은 단지의 여러 필지는 한 선택 대상에 합친다. 원천별 필지 귀속은 내부 근거에 남긴다.
확인되지 않은 평형 세대수·대지권·주차·용적률은 이전 값으로 채우지 않는다.
보정 경계는 점선으로 표시한다. 좌표만 있는 단지는 위치 점을 표시한다.

이는 공개 전환을 검토하는 경로다. 야간 생성·검색·임대 연결까지 현재 계약으로 전환한 뒤 운영 반영을 진행한다.

### 기존 사이트 확인

```text
npm run build:apartments -- --verify
npm run typecheck
npm run test:site
npm run test:api
npm run build
npm run preview
```

위 단지 검증 명령은 현재 리뷰 계약의 준비된 공개 자료를 대상으로 한다. BIN 전환 후보를 만들거나 공개 자료를 갱신하는 명령이 아니다. 테스트·전체 빌드는 작업 범위와 프로젝트 지침에 따라 선택한다.

미리보기는 `http://127.0.0.1:8793`이다. `/__preview/login`은 임시 DB의 테스트 계정으로 접속한다. 운영 로그인·사용자 DB와 연결되지 않으며 서버 종료 시 테스트 글은 사라진다. 이 도구는 공개 자산에서 제외된다.

## 운영 적용 순서

1. 검토된 변경을 `cloudflare-staging`에 배포한다. 기존 Staging workflow가 `0003_board_pins.sql`을 적용하고 테스트·빌드·배포 검증을 수행한다.
2. 스테이징에서 로그인, 글 작성, 다른 계정의 수정 차단, 공지·숨김·복구, 아파트 링크·뒤로 가기를 확인한다.
3. 동일한 검토 변경을 `main`에 반영한다. 2026-09-15 사용자 승인에 따라 Production workflow가 기존 GitHub 배포 토큰으로 `ensure-cloudflare-board-schema.mjs`를 실행한다.
4. 이 도구는 지정된 운영 계정·DB·main 실행과 기존 0001/0002 적용 상태를 확인한 뒤 `0003_board_pins.sql`의 고정된 CREATE TABLE 하나만 실행한다. 다른 SQL로 바뀌면 중단한다. 이미 있는 테이블은 열·외래키를 검증하고 보존한다. 테이블 추가 후 기록 단계가 중단돼도 재실행할 수 있다.
5. 공지 테이블 확인 후 Worker를 배포하고 공개 `/board/`, `/api/board/posts`, `/apartment/?id=41281-3250`와 동일 배포 SHA·자료 해시를 확인한다.

운영의 일반 마이그레이션 자동 실행은 여전히 사용하지 않는다. 이번에 명시 승인된 공지 테이블 추가만 예외이며 회원·댓글 내용, 다른 테이블, 인증 비밀값은 수정하지 않는다.

복구 시 이전 호환 Worker와 정적 자산을 사용하며 D1은 되감지 않는다. 새 테이블은 이전 코드와 공존하므로 삭제할 필요가 없다.
