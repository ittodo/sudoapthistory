# 공통 단지 자동완성

> 문서 역할: **기능·구현 설명** · [문서 목록](README.md)
> 현재 운영·공개 자료 계약은 문서 목록의 기준 문서를 따릅니다. 날짜·건수·성능 수치는 해당 검증 조건의 기록입니다.


현재 공통 검색 구현을 설명합니다. 최초 로컬 검증의 시각과 당시 미배포 상태는 [정리 전 기록](archive/apartment-search.md)에 보존합니다. 단지 수는 고정 계약이 아니며 현재 빌드 산출물에서 확인합니다.

## 화면 동작

- 단지 후보는 `송파구 · 리센츠`처럼 시군구를 앞에 표시한다. 둘째 줄은 동 이름이며 같은 이름·시군구·동의 후보가 겹칠 때 주소를 추가한다.
- 매매·전세·월세의 단지 검색, 지도, 실거래, 기간별 실거래, 통계, 비교 및 기존 단지/계약 목록에 같은 모듈을 연결했다. 단지 입력창이 없는 화면에는 검색창을 새로 만들지 않았다.
- 지역·시군구 범위의 전체 단지에서 최대 10개를 추천한다. 거래 기간·금액·면적 조건은 후보를 선택한 뒤 기존 본문 조회에 적용한다. 본문 정렬과 자유 입력, 평형 검색은 유지한다.
- 단지를 고르면 `searchApt`에 공통 식별자를 저장하고, 각 화면은 확인된 원천 식별자로 거래를 좁힌다. 비교 화면에서는 해당 단지의 평형 목록으로 좁힌 뒤 기존 평형 선택을 이어간다.
- 새로고침·공유·뒤로 가기·거래 유형 전환에서 선택을 복원한다. 입력 수정·초기화는 선택을 해제하고, 지역 범위를 벗어나는 선택은 해제 안내를 표시한다.
- 조건에 맞는 거래가 없으면 “단지는 있으나 현재 조회 조건에 맞는 거래가 없습니다”를 표시한다.
- 한글 조합 중에는 검색하지 않는다. 조합 완료/입력 후 150ms 지연, 이전 응답 무시, 방향키·Enter·Escape, 터치, combobox/listbox 및 실시간 안내를 지원한다. 첫 후보는 Enter만으로 자동 선택하지 않는다.
- 자료를 불러오지 못해도 기존 본문 검색을 사용할 수 있고 자동완성 재시도를 제공한다.

## 자료와 검색 규칙

`tools/build-search-data.mjs`가 빌드/로컬 서버 시작 시 아래 자료로 자동완성 목록을 구성한다. 목록은 ID 키 객체의 gzip JSON으로 포장하고 `/data/search/apartments.json`에는 manifest를 저장한다. 자동완성 목록 생성과 검색 Worker는 개별 거래 내역을 읽지 않는다. 함께 생성하는 홈 최신 가격 요약은 아래 절의 전월세 상태 스냅샷을 사용한다.

- `data/index.json`: 평형 행과 원천 식별자
- `data/apartments/index.json`: 공개 식별자 연결과 모호한 연결 목록
- 매매·전월세 manifest와 지역 번호표·metadata: regionalReader가 현재 공개 형식을 해석해 단지 카탈로그를 구성합니다. 과거 catalog.bin 고정 경로를 직접 요구하지 않습니다.
- `data/map/index.json`: 지도 식별자와 좌표
- `data/housing-v3/index.json`: 공개 단지 메타데이터와 공개 계약

연결이 확인된 식별자로만 합치고 이름이나 좌표 유사도로 합치지 않는다. 연결 미확정 전월세 단지는 `rental:<원천 ID>`로 유지한다. 등록된 이름 변형은 별칭에 보존한다. 숫자 시군구 코드는 기존 전월세 모델의 이름 변환을 재사용한다.

명시적으로 검토한 공개 그룹은 기존 대표 ID로 검색한다. 원래 단지명은 별칭으로 찾을 수 있다.
홈의 평형별 표는 원천 행과 투자지표를 유지한다. 통합 표는 그룹 이름과 중복 제거된
전체 세대수를 사용한다. 그룹 세대수가 미확인이면 원천 세대수를 더해 채우지 않는다.
홈 최신 요약의 `publicationGroup`은 이 표시 규칙을 구분한다.
구성원 선택과 원천 거래 보존은 [아파트 상세 계약](apartment-and-board.md)을 따른다.

공개 자동완성과 홈 최신 요약은 각각 32개 버킷을 사용한다. 단지 ID의 SHA-256 첫 바이트를 32로 나눈 나머지가 버킷 번호다. 다른 단지가 추가되어도 기존 ID의 버킷은 바뀌지 않는다.

| 파일 | 역할 |
| --- | --- |
| `data/search/apartments.json` | 자동완성 manifest. `schema: 1`, `format: gzip-json-records-v1`, 버전·버킷 경로·입력 및 출력 해시·해제 바이트 수 |
| `data/search/catalog/<버킷>-<SHA-256>.bin` | 자동완성 단지 레코드. 32개 |
| `data/search/latest-index.json` | 홈 요약 manifest. `format: gzip-json-records-v1`, 기준일·검색/전월세 버전·버킷 경로·입력 및 출력 해시·해제 바이트 수 |
| `data/search/latest/<버킷>-<SHA-256>.bin` | 단지 정보와 해당 단지의 최신 전세·월세 가격. 32개 |

파일명은 압축된 내용의 SHA-256을 포함한다. 확장자는 `.bin`을 유지하지만 압축을 풀면 `{단지 ID: 레코드}` 형태의 UTF-8 JSON이 나온다. manifest의 `format: gzip-json-records-v1`로 이 형식을 구분한다. `rawBytes[path]`는 해당 파일의 압축 해제 바이트 수다. reader는 실제 해제 크기를 이 값과 대조한다. 단지 DTO의 `PGRCD001` 형식과는 다르다.

manifest의 `inputs`는 원본 파일과 해시다. `sources`는 생성된 gzip 파일 경로와 해시다. 후보 수는 버킷에서 읽은 단지 레코드 수로 확인한다. [검색 생성기](../tools/build-search-data.mjs)가 원천 번호표·지역 자료와 공개 lookup을 합친다. 포장 단계는 `inputs`를 실제 원본 자산의 해시와 대조한다. 공개 계약과 후보 차단은 아래 로컬 실행 절을 따른다. 전체 자료 역할은 [자료 사용 계약](site-layout.md#페이지-기능별-데이터-사용-계약)을 따른다.

`tools/packed-asset-cache.mjs`는 비공개 계산 캐시에 버킷별 논리 내용·직렬화 및 압축 코드 지문·출력 해시를 저장한다. 재사용 근거와 저장된 바이트가 맞으면 포장을 생략한다. 한 단지의 값이 바뀌면 그 단지가 속한 버킷만 다시 포장한다. 목록 구성과 입력 확인 자체를 생략한다는 뜻은 아니다.

2026-09-20 검증 당시 자료 버전: `ed3ff04ed6e96b6da0f046970b3b31bf3a46b22e965e2daf09b5d5cb42ad9377`.

[es-hangul](https://github.com/toss/es-hangul) **2.4.0**을 정확한 버전으로 고정했다. 초성 추출과 자모 분해에 사용하며, 순위 계산은 `js/apartment-search-model.js`에 있다. MIT 라이선스와 라이브러리를 Worker 번들에 포함해 자체 제공한다.

정확 일치 → 앞부분 일치 → 부분 일치 → 초성/입력 중 자모 → 가벼운 오타 순서로 정렬한다. NFKC·대소문자·공백·괄호 차이를 정리하되 숫자와 괄호 안 단어는 남긴다. 여러 단어는 모두 이름/별칭 또는 지역/주소와 맞아야 하며 지역에는 오타를 허용하지 않는다. 이름 오타는 한글 세 음절 이상, 자모 편집거리 비율 0.25 이하로 제한한다. 명시한 단지·차수 번호가 다른 후보는 제외한다. 동순위는 거리·길이 차이·이름·주소·식별자로 안정 정렬하며 백분율 점수를 표시하지 않는다.

문서당 Worker 하나가 첫 검색 사용 시 `packedDataset.all()`로 32개 버킷 전체를 읽고 검색 객체를 만든다. 준비한 색인은 같은 문서에서 재사용한다. 지역별 후보를 먼저 좁힌다. 식별자가 있는 URL을 복원할 때도 동일한 목록을 사용한다.

`packedDataset`은 파싱한 버킷 객체를 LRU 캐시에 보관한다. 유지된 객체는 다시 파싱하지 않고 ID 속성으로 조회한다. 최대 4개·해제 바이트 합계 64MiB를 보관하며, 용량 계산에는 검증한 `rawBytes`를 사용한다. 퇴거된 버킷을 다시 읽으면 해제와 파싱이 필요하다. 호환 BIN 경로는 열린 버퍼와 색인을 보관하고 `get()`마다 선택 객체를 복원한다. JSON과 BIN의 객체 보유 방식은 다르다.

공용 검증 파일 캐시는 압축된 다운로드 바이트를 최대 256개·64MiB까지 Cache Storage에 보관한다. 다른 릴리스에서도 내용 해시가 같으면 같은 파일을 재사용한다. 이 한도와 `rawBytes` 예산은 실제 JS 힙이나 전체 검색 객체의 메모리 상한이 아니다. 상세 캐시 규칙은 [공통 자료 계약](site-layout.md)을 따른다.

Worker는 기존 `apartments` 배열이 들어 있는 JSON과 `packed-records-v1` 버킷도 읽는다. 현재 리뷰 후보 미리보기는 기존 JSON 배열 경로를 유지한다. 홈 로더도 이전 지역별 gzip JSON 요약과 `packed-records-v1` 버킷을 읽을 수 있다.

## 전송 형식 선택 근거 (2026-10-23)

현재 검색과 홈 필터는 처음부터 전체 목록을 만든다. 같은 32개 버킷과 같은 값으로 비교한 결과, gzip JSON이 generic ValueNode BIN보다 작고 최초 전체 읽기도 빨랐다. 고정 ID 버킷과 내용 해시 파일명은 유지하고 본문 형식만 gzip JSON으로 정했다.

| 자료 | 레코드 수 | gzip BIN | gzip JSON | 최초 전체 읽기 BIN | 최초 전체 읽기 JSON |
| --- | ---: | ---: | ---: | ---: | ---: |
| catalog 32개 | 20,917 | 2,634,038 B | 1,869,463 B | 586.78ms | 140.04ms |
| latest 32개 | 20,917 | 7,711,653 B | 6,564,876 B | 2,310.33ms | 445.47ms |

크기는 32개 압축 본문의 합계이며 manifest는 제외한다. 최초 전체 읽기는 gzip 해제, BIN 레코드 색인 열기 또는 JSON 파싱, 전체 레코드 복원, 키 정렬과 값 목록 생성을 포함한다. 검색 모델의 초성·자모 색인 준비 시간은 포함하지 않는다. 모든 ID의 값은 정확히 같음을 확인했다.

측정은 Windows의 Node 22.18.0에서 각 구간을 5회 실행한 중앙값이다. gzip level 6을 사용했고 BIN/JSON 실행 순서를 번갈아 적용했다. 압축 바이트는 메모리에 있었으며, 측정 전 GC 시간과 다운로드·파일 읽기·해시 확인·Cache Storage·화면 렌더링은 제외했다. 별도 전체 빌드가 동시에 실행되어 절대 시간은 참고값이다. 브라우저나 모바일의 최초 표시 시간으로 해석하지 않는다.

JSON도 파싱한 객체의 ID 키로 직접 접근할 수 있다. BIN의 선택 복원은 전체 객체를 보유하지 않아도 되는 이점이 있다. 현재 검색처럼 모든 객체를 만드는 소비 경로에는 그 이점이 적용되지 않는다. 이 측정을 공통 거래의 전용 BIN 스키마나 단지 상세의 선택 조회로 일반화하지 않는다. [측정 보고서](../../_ops/reports/packed-transport-20261023/search-transport-benchmark.md)와 [5회 표본](../../_ops/reports/packed-transport-20261023/search-transport-benchmark.json)에 조건과 구간별 결과를 보관한다.

## 검증

현재 변경의 회귀 검사는 다음 명령을 사용한다.

- `npm run test:search`: 정규화·순위·초성·혼합 자모·오타·지역 조합·번호·동명 단지·후보 제한, 실제 자료, 연결 분리, 평형 중복 제거, 조건 적용, 키보드, 한글 조합, 응답 순서 경합, URL 복원, 오류/재시도.
- `node --test tools/test-cloudflare-packed-assets.mjs tools/test-cloudflare-home-search.mjs`: 내용 해시 버킷 재사용, 홈/자동완성 번들, 실패 재시도, 버퍼 개수·용량 제한, 원본 행·단지 식별자 보존.

2026-10-23 gzip JSON 전환의 로컬 검증에서 `test:search`는 12개, packed assets 검사는 6개, home search 검사는 7개를 통과했다. 전체 운영 배포의 완료를 증명하는 검사는 아니다.

같은 날 실제 검색 버킷 64개를 제품의 `packedDataset.all()`과 Node의 `DecompressionStream`으로 읽었다. catalog와 latest 각각 20,917개 레코드의 모든 키·값이 같았고, 최신 가격은 106,172개였다. 파일 해시·해제 크기·ID별 버킷도 확인했다. [실자료 판독 검산](../../_ops/reports/packed-transport-20261023/search-json-reader-audit.json)은 읽기 전용 캐시에서 manifest를 재구성한 결과다. 최종 배포 manifest나 브라우저 표시를 검증한 결과는 아니다.

아래는 2026-09-20 JSON 목록 형식의 검증 기록이다.

- `npm run test:site`: 60개 통과.
- `npm run test:daily`, 전월세 모델 및 Worker 검사, `npm run typecheck`: 통과.
- `npm run build`: 통과. 검색 JSON과 Worker가 배포 manifest에 포함되고 원본/결과 해시가 일치하는 것을 확인했다.
- 실제 브라우저에서 단지 검색, 매매/전월세 지도·실거래·기간별 실거래·비교·통계, 전세 시장 동향/순위, 기존 단지 목록을 확인했다. 리센츠 선택, 반포자이 선택, 지역 변경 해제, 기존 `25평` 검색, 현재 조건에 거래가 없는 경우, 매매→월세 전환, 선택 전 자유 입력으로 뒤로 가기와 앞으로 가기를 확인했다.
- 390×844 화면에서 후보창과 문서의 가로 넘침이 없었다. 세로 스크롤바가 있는 경우에도 후보창을 문서의 실제 표시 폭 안에 맞춘다.

## 과거 성능 측정: JSON 목록 (2026-09-20)

환경: Windows 10.0.26200, AMD Ryzen 7 6800H, 논리 코어 16개, Node 22.18.0. 당시 전체 단지 20,929개, JSON 6,080,985바이트, 자체 제공 Worker 11,730바이트였다. 아래 수치는 현재 gzip JSON 버킷 크기나 최초 다운로드 성능을 나타내지 않는다.

`npm run bench:search`는 별도 Node Worker에서 실제 전체 목록으로 14종 입력을 준비 후 8회씩, 총 112회 측정한다.

| --- | ---: |
| JSON 해석과 색인 준비 | 285.35ms |
| 색인 준비 후 추가 JS heap | 36.35MiB |

브라우저는 입력 지연 150ms를 제외하고 Worker 요청부터 결과 반영 후 두 번의 animation frame까지 측정했다. 인앱 브라우저, 동일 PC에서 준비된 색인을 사용한 표본이다.

| 화면 크기 | 입력 | Worker 검색 | 결과 표시 |
| --- | --- | ---: | ---: |
| 1440×1000 | `리센ㅊ` | 20.00ms | 42.70ms |
| 1440×1000 | `잠실 리센트` | 31.30ms | 60.60ms |

표본에서 데스크톱 100ms 목표를 충족했다. 390px 측정은 PC에서 모바일 화면 폭을 적용한 결과로, 실제 모바일 기기의 200ms 목표와 메모리 사용량은 별도 기기 검증이 필요하다. 최초 목록 다운로드 시간은 위 준비 후 검색 시간에 포함하지 않는다. heap 값도 브라우저 전체 메모리가 아닌 Node Worker의 색인 추가 사용량이다.

## 홈 단지·평형 목록과 최신 가격 요약

홈의 매매·전세·월세는 기존 스크리너의 표, 모바일 카드, 검색, 정렬, 페이지 이동과 평형 통합을 함께 사용한다. 날짜별 계약 통계는 실거래·통계 화면에 남긴다. 원본 매매 행 번호와 계산 지표는 유지하며 승인된 공통 검색 카탈로그로 전월세 전용 평형을 추가한다. 이름·좌표로 연결하지 않는다. 거래가 없는 유형은 ‘거래 없음’으로 표시하고 정렬 마지막에 둔다. 전월세 전용이라는 이유로 임대 단지로 분류하지 않는다.

`build-search-data.mjs`의 기존 자산 포장 단계가 `build-home-search-data.mjs`를 호출한다. 이미 생성된 최신 전월세 상태 스냅샷의 opening/updates를 접어 최신 유효 계약을 고르고, 기존 rental-model의 해제 제외·환산 계산을 재사용한다. 단지·반올림 평형·유형별 최신 계약일, 동률 시 원천 거래 ID 순서를 사용한다. 실제 계약 면적과 원천 ID도 보존한다. 환산율이 없으면 원금액만 표시한다.

- 공개 파일은 위 표의 `latest` 32개 gzip JSON `.bin`과 `latest-index.json`이다. 단지 ID 키로 단지 정보와 최신 가격 배열을 함께 저장한다.
- 브라우저는 최초 전체 필터 목록을 만들 때 32개 버킷을 모두 읽는다. 요약과 동일 입력 해시의 매매 인덱스도 검증한다. 문서 내 동시 호출과 탭 전환은 같은 Promise/자료를 재사용한다. 새 문서에서는 내용 해시가 같은 압축 파일을 공용 캐시에서 읽는다. 홈에서는 과거 월 파일이나 전체 계약 이력을 받지 않는다. 상세를 열 때만 기존 이력 조회를 사용한다.
- 지역·동·단지·면적·세대수·준공연도는 공통이고 가격 범위·정렬은 유형별 URL/로컬 상태에 보관한다. 지도에서 저장한 과거 날짜는 홈 조회에 사용하지 않는다. 전월세에는 매매 투자지표 필터를 적용하지 않는다.
- 상세는 기존 패널/모바일 상세를 연다. 연결 미확정 ID는 공통 카탈로그의 정확한 원천 ID만 사용해 같은 상세의 전월세 이력을 조회한다. 다른 단지로 대체하지 않는다.

2026-09-22의 지역별 gzip JSON 형식 측정에서는 원본 41,342행을 유지한 공통 목록이 과거 단지 포함 61,456행이었다. 기본 과거 단지 제외 목록은 61,416행이었다. 당시 요약 포장 표본은 약 3.9초, 지역 파일 합계 약 5.57MB(압축)였다. 현재 ID 해시별 32개 버킷의 크기·처리 시간과 구분한다. 원장 재생성 시간이나 모바일 네트워크 시간은 포함하지 않았다.

## 로컬 실행

`npm ci` 후 `npm run preview`로 실행한다. 기본 주소는 `http://127.0.0.1:8793`이다. 검색 모델 또는 원본 자료를 변경하면 로컬 서버를 다시 시작해 생성된 자료와 Worker를 갱신한다. 운영 산출물은 `npm run build`로 생성되며 이 작업만으로 운영 배포되지는 않는다.

현재 리뷰 후보의 검색은 `tools/prepare-current-review-search.mjs`로 별도 준비한다. 후보의 평형 행·상세 식별자·지도·단지 정보와 기존 공개 자료의 매매·전월세 단지 번호표만 합친다. 거래 내역은 읽지 않는다. 같은 공개 단지에 여러 원천이나 필지가 있어도 기존 식별자 연결을 유지한다. 결과는 후보 폴더의 `data/search/apartments.json`에 단지 배열이 든 기존 JSON으로 저장한다. 후보 경로는 32개 gzip 버킷 포장으로 전환하지 않는다.

현재 원천이나 지역 근거가 없는 보존 단지는 “지역 미확인”으로 이름 검색에 남긴다. 지역을 추측해서 채우지 않는다. 상세 갱신은 기존 거래·면적·댓글 ID를 유지하고 충돌 없는 새 원천 링크만 추가한다. 다른 공개 ID가 가진 링크는 덮어쓰지 않고 미확정으로 표시한다. 임대 표시는 현재 임대 근거가 있을 때만 적용한다.

후보는 `_ops` 아래의 별도 폴더여야 한다. 후보 manifest의 `candidateOnly`는 `true`여야 한다. 주택 메타데이터도 `candidateOnly: true`, `approvedOnly: false`여야 한다. 운영 검색 생성기는 후보를 받지 않는다. 아래 `CANDIDATE_DIRECTORY`를 준비된 후보의 절대 경로로 바꾼다.

```text
node tools/prepare-current-review-search.mjs D:/Work/sudoapthistory CANDIDATE_DIRECTORY
node tools/prepare-current-review-timeline.mjs D:/Work/sudoapthistory CANDIDATE_DIRECTORY
node tools/preview-current-review.mjs CANDIDATE_DIRECTORY
```

후보 미리보기는 `http://127.0.0.1:8794/map/`이다. 공개 데이터는 후보 파일을 우선 읽고 나머지 공유 거래 파일은 기존 소스에서 읽는다. HTML·JS·CSS는 현재 소스를 사용한다. GET·HEAD만 허용하며 로그인 API와 운영 쓰기는 연결하지 않는다. 화면에 “현재 리뷰 데이터 미리보기 · 운영 미반영”을 표시한다. 내부 evidence와 manifest는 제공하지 않는다.

타임라인 후처리는 후보의 일별·전월세 manifest를 현재 지도 버전에 연결한다. 일별 manifest의 지도 파일 해시와 이에 종속된 미리보기 버전도 갱신한다. 검색 목록에는 실제 제공되는 두 manifest의 해시를 넣는다. 거래 파일·원천 revision·단지 번호표·가격 통계는 바꾸지 않는다. 전월세 자료 버전은 기존 계약 상세와 맞도록 보존한다. 준비된 후보에도 별도로 실행할 수 있다. 기존 공개 단지 ID가 빠졌거나 후보 manifest에 지도 참조 외 변경이 있으면 중단한다. 운영 자료와 공개 모드 선택에는 영향을 주지 않는다.

이전 검색·지도 가격 캐시·단지 외곽선은 후보 대신 제공하지 않는다. 후보에 가격 캐시가 없으면 지도는 공유 거래 자료로 조회한다. 없는 검색 Worker 번들만 기존 포장 결과를 재사용한다. 준비된 검색의 입력 해시는 미리보기가 실제 제공하는 파일과 일치해야 한다.

합친 단지 외곽선은 `data/map/boundaries/{g}.json`에 저장한다. 상세 DTO의 `map.boundary`는 공개 지도 ID, 시군구와 경계 근거를 참조한다. 검색 목록에는 도형을 복제하지 않는다. 지도에 선언한 외곽선 샤드 해시는 상세 인덱스와 후보 검색 JSON의 `sources`에도 포함한다. 정식 버킷 검색 manifest에서는 같은 원본 근거를 `inputs`에 둔다. 후보 경계가 없거나 해시가 다르면 준비를 중단한다. 외곽선의 생성·표시는 [지도 문서](map-explorer.md)를 따른다.

전용 검증은 `node --test tools/test-prepare-current-review-search.mjs tools/test-prepare-current-review-timeline.mjs tools/test-preview-current-review.mjs`로 실행한다. 임시 자료로 원천·식별자 보존, 입력 해시, 타임라인 초기화, 후보 우선순위, 읽기 전용 요청과 비공개 경로 차단을 확인한다.

정식 현재 리뷰 계약의 Node 지원은 구현했지만 운영 전환은 아직 적용하지 않았다. 정식 자료는 주택·지도 메타데이터의 `contract`가 모두 `current-review-publication-v1`이고 `candidateOnly`가 모두 `false`여야 한다. 주택의 `approvedOnly`는 `false`여야 한다. 주택 `sourceVersion`과 지도 `publicationSourceVersion`도 같아야 한다. 지도 `sourceVersion`은 최종 행정 구역 연결까지 반영한 별도 버전이다. 기존 공개 형식은 `approvedOnly: true` 조건을 유지한다. 이 계약은 개별 검토 항목의 승인을 뜻하지 않는다.

정식 상세 생성 경로는 생산자가 준비한 version 2 DTO를 재사용한다. 기존 거래·면적·댓글 ID를 다시 집계하지 않는다. `--verify`를 지정했을 때만 기존 상세 검증을 실행한다. 정식 검색은 후보와 같은 “지역 미확인” 처리를 쓴다. 현재 원천이 없다고 명시된 거래 없는 보존 단지만 이 처리를 받을 수 있다. 거래 원천의 지역 누락은 계속 오류로 처리한다.

생산자 검증 결과의 `checks.currentReview`는 계약, 원천 버전, 주택·지도 파일 해시와 `individualApprovals: preserved_from_workbench`를 보존한다. 최종 `verify-housing-regions.mjs`는 실제 주택·지도 파일의 계약과 버전 연결을 확인하고 이 값을 구성한다. 완료 기록을 만들 때 manifest에 연결된 해시와 다시 대조한다. 기존 일별·전월세·거래 상세·아파트 DTO 검증 결과는 그대로 필요하다. 이전 `buildingAudit` 성공 결과를 대신 만들어 넣지 않는다. 후보 자료나 서로 다른 원천 버전은 완료 기록을 만들 수 없다. CLI 진입점은 일반 경로와 Rust가 전달하는 Windows 확장 경로(`\\?\D:\…`)를 같은 파일 URL로 판정한다. 두 경로 모두 검증을 실행하고 JSON 결과를 출력한다. 모듈을 import할 때는 자동 실행하지 않는다. 관련 독립 검증은 `node --test tools/test-verify-housing-regions.mjs tools/test-housing-publication-contract.mjs tools/test-cloudflare-apartment-sale.mjs tools/test-validation-session.mjs`로 실행한다.

## 예약 배포 호환

운영/시험 배포 모두 `test:search`를 실행한다. 실제 카탈로그 검사는 고정된 단지 수를 전제하지 않고 해당 빌드의 매매·전월세 원천 전체가 포함되는지 대조한다. 수집으로 단지가 추가되거나 승인된 연결이 바뀌어도 최신 원본으로 검색 목록을 구성한다. 공개 gzip JSON 버킷·manifest·Worker는 `cloudflare/dist/public`에 포장한다. 버킷 재사용 근거는 `cloudflare/dist`의 비공개 캐시에 저장한다. 원본 자료나 Git 추적 파일을 생성 결과로 덮어쓰지 않는다. 별도의 검색 자료 생성 예약은 필요 없다.
